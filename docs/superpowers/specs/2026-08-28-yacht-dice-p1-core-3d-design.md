# Yacht Dice — P1: 코어 규칙 엔진 + 3D 주사위 설계

- 작성일: 2026-08-28
- 상태: 승인 대기
- 범위: P1 (코어 + 3D + 싱글 플레이). P2~P4는 로드맵으로만 기록.

## 1. 목표

레퍼런스(닌텐도 『세계의 게임 대전 51』 Yacht Dice)의 물성과 규칙을 따르는
iOS 네이티브 야추 다이스 게임. 최종적으로 온라인 대전을 포함해 App Store에 출시한다.

P1의 목표는 **혼자서 처음부터 끝까지 플레이할 수 있는 앱**이며,
동시에 P3(온라인)에서 코어를 갈아엎지 않아도 되는 구조를 확립하는 것이다.

## 2. 전체 로드맵

| 단계 | 내용 | 완료 시점 |
|---|---|---|

## 4. 게임 규칙 명세

### 4.1 진행

- 총 **12턴**. 매 턴 주사위 5개를 굴린다.
- 턴당 최대 **3회** 굴림. 1회차는 5개 전부, 2~3회차는 keep하지 않은 주사위만.
- 굴림 사이에 각 주사위를 개별적으로 keep/unkeep 할 수 있다.
- 턴을 마치려면 아직 비어 있는 카테고리 **하나**에 점수를 기록한다.
  조건을 만족하지 못해도 기록할 수 있으며 이 경우 0점(scratch)이 된다.
- 12턴 후 모든 카테고리가 채워지고 총점이 확정된다.

### 4.2 점수표

| 카테고리 | 조건 | 점수 |
|---|---|---|
| Aces | — | 눈이 1인 주사위의 합 |
| Deuces | — | 눈이 2인 주사위의 합 |
| Threes | — | 눈이 3인 주사위의 합 |
| Fours | — | 눈이 4인 주사위의 합 |
| Fives | — | 눈이 5인 주사위의 합 |
| Sixes | — | 눈이 6인 주사위의 합 |
| **상단 보너스** | 위 6개 소계 ≥ 63 | **+35** |
| Choice | — | 주사위 5개 총합 |
| 4 of a Kind | 같은 눈 4개 이상 | 주사위 5개 **총합** |
| Full House | 3개 + 2개 (5개 동일도 인정) | 주사위 5개 **총합** |
| S. Straight | 연속된 눈 4개 이상 (1234 / 2345 / 3456) | **15 고정** |
| L. Straight | 연속된 눈 5개 (12345 / 23456) | **30 고정** |
| Yacht | 같은 눈 5개 | **50 고정** |

- 조커 룰 없음. 야추 추가 보너스 없음.
- 4 of a Kind는 5개 동일도 만족한다.
- 상단 보너스는 12턴 종료 시점이 아니라 소계가 63에 도달하는 즉시 확정 표시한다.

```
SwiftUI Views ──관찰──▶ GameSession  (@Observable, @MainActor)
                          ├─▶ YachtCore.GameState   (순수 규칙, 의존성 0)

```

원칙:

- `YachtCore`는 **별도 Swift Package**이며 SwiftUI·RealityKit·네트워크를 import하지 않는다.
  레이어 경계를 컴파일러가 강제하게 만드는 것이 목적이다.

- `GameSession`이 유일한 오케스트레이터다.

## 6. YachtCore

### 6.1 이벤트 소싱

**의도(Intent)와 사실(Event)을 분리**한다. 이것이 P3 확장의 근거다.

```swift
/// 플레이어가 하고 싶은 것. 출처(터치/AI/네트워크)를 코어는 모른다.
enum Intent {
    case roll
    case toggleHold(Int)        // 주사위 인덱스 0..<5
    case commit(Category)
}

/// 확정된 사실. 주사위 눈이 "이미 정해진 채로" 들어온다.
enum Event: Codable, Equatable {
    /// 굴린 주사위의 새 눈. keep되지 않은 슬롯에 인덱스 오름차순으로 채워진다.
    /// 예) held = {1, 3} 이고 rolled([5, 2, 6]) 이면 슬롯 0←5, 2←2, 4←6.
    /// 따라서 배열 길이는 항상 (5 - held.count) 와 같아야 하며, 다르면 불법 이벤트다.
    case rolled([Int])
    case holdToggled(Int)
    case committed(Category, Int)   // 카테고리 + 확정 점수
    case turnAdvanced
    case gameEnded
}

struct GameState: Equatable {
    /// UI 버튼 활성화 판단용. 부작용 없음.
    func validate(_ intent: Intent) -> Result<Void, RuleError>
    /// 순수 함수. 같은 로그를 리플레이하면 같은 상태가 나온다.
    func applying(_ event: Event) -> GameState
}
```

RNG는 코어 **밖**에 있다.

- P1 로컬: `SystemRandomNumberGenerator`
- P3 온라인: Supabase Edge Function이 굴린 결과
- 테스트: 대본 (`[6,6,6,6,6]`)

코어 입장에서는 셋 다 똑같이 "이미 정해진 숫자"다.

### 6.2 P3에서 얻는 것

이 구조 덕분에 온라인 대전은 **`Event` 배열을 주고받는 것**이 전부가 되고,
재접속은 이벤트 리플레이, 관전·전적·리플레이도 같은 메커니즘으로 따라온다.
지금 이 형태로 만들지 않으면 P3에서 코어를 재작성해야 한다.

### 6.3 주요 타입

- `Category`: 12개 케이스 enum. `func score(_ dice: [Int]) -> Int` 를 순수 함수로 제공.
- `ScoreCard`: `[Category: Int?]`, `upperSubtotal`, `upperBonus`, `total` 파생 계산.
- `TurnState`: `rollsRemaining` (3→0), `dice: [Int]`, `held: Set<Int>`.
- `GameState`: `players`, `scorecards`, `currentPlayerIndex`, `turnIndex` (1...12), `phase`.
- `Phase`: `awaitingFirstRoll` (아직 안 굴림, commit 불가) / `rolling` (1회 이상 굴림, keep·재굴림·commit 가능)
  / `finished` (12턴 종료). `validate(_:)`가 어떤 Intent를 허용할지 판단하는 근거다.
- `RuleError`: `noRollsRemaining`, `categoryAlreadyUsed`, `mustRollFirst` 등.

P1에서 `players`는 1명이지만 자료구조는 처음부터 다인용으로 만든다.
P2에서 인원만 늘리면 되게 하기 위함이며, 추가 비용이 거의 없다.

## 7. 3D 씬과 궤적 시스템

### 7.1 문제

RealityKit 물리는 프레임 타이밍·부동소수점 차이로 기기마다 결과가 갈린다.
온라인 대전에서는 두 화면에 같은 눈이 떠야 하고 서버가 그 눈을 믿을 수 있어야 한다.
따라서 **"물리가 결과를 만든다"가 아니라 "결과가 먼저 정해지고 물리는 연출한다"** 로 뒤집는다.

기각한 대안: 자유 물리로 굴린 뒤 정지 직전에 목표 면으로 회전 보정하는 방식.
보정각이 180°에 가까울 때 눈에 띄게 튀고, 주사위 5개가 서로 충돌하면 더 심해진다.

### 7.2 채택안 — 프리베이크 궤적 + 회전 오프셋

**던지는 궤적과 나오는 눈을 완전히 분리한다.**

**베이킹 (개발 시 1회)**
별도 macOS 베이커 툴로 주사위가 트레이 벽·서로와 충돌하며 굴러가는 물리 시뮬을 돌려
매 프레임의 위치와 회전, 그리고 정지 시 최종 자세를 기록한다.
기록 직후 각 주사위의 최종 자세를 **가장 가까운 축정렬 자세(24개 중 하나)로 정확히 스냅**한다.

- 굴리는 개수 1~5개 × 던지는 방향 3종(좌/중앙/우) × 변형 40개 ≈ 600 궤적
- 프레임당 위치(3×float16) + 회전(4×int16) = 14바이트로 양자화, 2초 @60fps 기준 총 약 3MB
- 충돌 타임스탬프를 함께 기록 (사운드·햅틱 트리거용)

**런타임 재생**
궤적 하나를 고르고, **위치는 그대로 재생하되 각 주사위의 회전에만 오프셋을 곱한다.**

```
q'(t) = q(t) · Δ,   Δ = q_final⁻¹ · q_target
```

`q_target`은 목표 눈 v가 위를 향하는 축정렬 자세다.
그런 자세는 (Y축 자전만큼) 4개 있으므로 매번 무작위로 골라 다양성을 준다.
`t = final`을 대입하면 `q'(final) = q_final · q_final⁻¹ · q_target = q_target` 이므로
목표 눈이 정확히 위를 향한다.

### 7.3 이 방식이 근사가 아니라 정확한 이유

`q_final`과 `q_target`이 **둘 다 축정렬 자세**이므로, `Δ = q_final⁻¹ · q_target` 는
정육면체의 **24개 회전 대칭군(octahedral group)의 원소**다.

Δ가 정육면체의 대칭이라는 것은 `Δ · (정육면체 점집합) = (정육면체 점집합)` 을 뜻한다.
따라서 매 프레임 t에 대해

```
q(t)·Δ 를 적용한 주사위 = q(t) 를 적용한 (Δ·주사위) = q(t) 를 적용한 주사위
```

즉 **회전된 주사위는 매 프레임 원본과 정확히 같은 공간을 점유한다.**
벽·바닥·다른 주사위와의 접촉점까지 전부 동일하다.
움직이는 것은 표면에 그려진 눈뿐이다.

결론: 이것은 "그럴듯해 보이는 눈속임"이 아니라 **물리적으로 완전히 동일한 궤적**이다.
이 성질은 최종 자세가 정확히 축정렬일 때만 성립하므로, 베이킹 시의 스냅 처리와
7.6의 검증 테스트가 필수다.

### 7.4 얻는 것과 치르는 값

얻는 것:
- 두 기기 화면이 프레임 단위로 동일 → 온라인 대전 성립
- 물리 시뮬 미실행 → 배터리·발열 절약, 저사양 기기에서도 프레임 안정
- 리플레이·관전이 "궤적 ID + 결과값" 몇 바이트로 표현됨

치르는 값:
- 베이커 툴을 별도로 만들어야 한다
- 트레이 치수나 주사위 물성을 바꾸면 다시 구워야 한다 → 씬 튜닝 완료 후 굽는 순서로 관리
- 카메라 자유 회전, 주사위를 손으로 집어 던지는 자유 물리 상호작용은 포기
  (레퍼런스도 고정 시점이므로 제품 손실 없음)

### 7.5 씬 구성

`RealityView` 안에:

- 고정 `PerspectiveCamera` — 레퍼런스와 같은 약 55° 부감
- 정적 엔티티: 나무결 테이블, 가죽 트레이(바닥 + 벽 4면)
- 동적 엔티티: 주사위 5개 (재생 중에는 물리 비활성, 키프레임 구동)
- 조명: `ImageBasedLightComponent`(소형 스튜디오 HDR) + 그림자용 방향광 1개

재질은 전부 `PhysicallyBasedMaterial`.
주사위는 흰 세라믹(roughness 0.35 + clearcoat, 눈은 노멀맵으로 오목하게),
가죽·나무는 albedo/roughness/normal 3종 텍스처.
레퍼런스의 "따뜻한 실내 조명에 놓인 실물" 질감은 대부분 IBL이 만든다.

keep한 주사위는 트레이 상단 선반으로 올라가고 굴림 대상에서 빠진다.

에셋은 Reality Composer Pro 씬 하나(`YachtScene.usda`)로 관리하고
코드에서는 이름으로 엔티티를 찾아 붙인다.

### 7.6 던지기 인터랙션

- 스와이프 방향으로 던지면 해당 방향 그룹의 궤적을 고른다
- Roll 버튼도 병행 제공 (제스처 전용으로 두지 않는다 — 접근성)
- `Reduce Motion` 활성 시 궤적 재생을 건너뛰고 결과를 즉시 표시

## 8. 상태 관리

### 8.1 MatchDriver

P2·P3의 확장점.

```swift
protocol MatchDriver {
    func requestRoll(keeping: [Int]) async throws -> [Int]  // 눈의 출처
    func submit(_ event: Event) async throws                 // 상대에게 전파
    var incoming: AsyncStream<Event> { get }                 // 상대 행동 수신
}
```

P1에는 `LocalDriver` 하나뿐이며 `incoming`은 빈 스트림이다.
P3에서 `OnlineDriver`를 끼우면 뷰와 코어는 한 줄도 바뀌지 않는다.

### 8.2 연출 큐 — 놓치기 쉬운 지점

이벤트가 발생하면 `GameState`는 **즉시** 전이하지만,
화면은 주사위가 굴러가는 약 1.8초 동안 뒤처져 있어야 한다.
점수판 미리보기 숫자가 주사위 착지보다 먼저 뜨면 게임이 망가진다.

따라서 `GameSession`은 연출 큐를 두고 `DiceStage`의 재생 완료를 `await`한 뒤에야
새 상태를 뷰에 노출한다. P3에서 상대 턴을 볼 때도 같은 큐를 그대로 쓴다.

## 10. 저장과 복원

이벤트 소싱 덕분에 진행 중인 게임 저장은 **이벤트 로그를 파일로 쓰는 것**이 전부다.
앱을 강제 종료해도 리플레이로 복원된다.
P3의 재접속과 정확히 같은 메커니즘이므로 두 번 만들지 않는다.

- **점수 전수 검증**: 주사위 조합 6⁵ = 7,776개 × 12 카테고리 = 93,312 케이스를
  전부 계산해 골든 파일과 대조한다.
- **불변식 (property-based)**: 임의의 합법 이벤트 시퀀스를 생성해
  ① 12턴 후 모든 칸이 채워지는가 ② 총점이 항목 합 + 보너스와 일치하는가
  ③ 같은 이벤트 로그를 리플레이하면 같은 상태가 나오는가.
  ③은 P3 재접속의 안전장치다.
- **궤적 데이터 검증**: 구운 모든 궤적에 대해
  ① 최종 자세가 축정렬 6면 중 하나와 2° 이내로 일치하는가
  ② 주사위가 트레이 밖으로 나가지 않는가
  ③ **각 궤적 × 목표 눈 1~6 조합에서 회전 오프셋 적용 후 위로 오는 면이 정확히 목표 눈인가**

  ③이 이 프로젝트에서 가장 중요한 테스트다. 여기가 깨지면 온라인 대전이 통째로 무너진다.
- **UI**: 3D 때문에 스냅샷 테스트는 불안정하므로 하지 않는다.
  `GameSession` 레벨 테스트 + XCUITest 스모크(12턴 완주, 앱 재시작 복원)로 대신한다.
- 3D 연출 자체는 테스트로 잡을 수 없으므로 궤적 데이터 검증과 수동 확인으로 커버한다.

## 13. 가정

- **3D 에셋**: 주사위·트레이·테이블 지오메트리는 코드 또는 Reality Composer Pro에서
  직접 생성한다 (전부 박스 / 모따기 박스라 모델러가 필요 없다).
  텍스처는 CC0 PBR 소스(나무·가죽)를 사용하고, 주사위 눈은 절차적 노멀맵으로 만든다.
  **P1은 외부 3D 아티스트 없이 진행한다.**
- 사운드·햅틱은 P1에서 훅만 심어두고(궤적의 충돌 타임스탬프 활용) 실제 에셋은 P4에서 채운다.
- 현지화는 P4. P1은 한국어/영어 문자열을 코드에서 분리해두기만 한다.

## 14. 리스크

**① 베이커 툴 (높음)**
headless macOS에서 RealityKit 물리를 돌리는 것은 검증되지 않은 경로다.
완화: 창 있는 소형 macOS 앱으로 만들어 확실히 구동한다.
그래도 막히면 주사위-박스 충돌만 다루는 자체 강체 시뮬(수백 줄 규모)로 대체한다.
**P1 착수 직후 이것부터 스파이크로 확인한다.** 여기서 막히면 7장 전체가 흔들린다.

**② 세로 화면의 점수판 밀도 (중간)**
12칸 + 소계 + 보너스 + 총점이 iPhone 세로 하단 절반에 들어가야 한다.
완화: 초기에 실제 기기에서 레이아웃부터 검증하고, 필요하면 점수판을
확장 가능한 하단 시트로 전환한다.

## 15. P1 완료 기준

- 혼자 12턴을 끝까지 플레이할 수 있다
- 점수와 상단 보너스가 93,312 케이스 전수 검증을 통과한다
- 주사위 3D 굴림 결과가 목표 눈과 100% 일치한다 (궤적 × 눈 전수 검증 통과)

- 앱 강제 종료 후 진행이 복원된다
- iOS 18 지원 최저 기기에서 60fps를 유지한다
